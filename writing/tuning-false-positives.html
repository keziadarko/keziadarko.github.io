Cutting SIEM false positives without missing real threats

A practical approach to tuning noisy detection rules: measure, understand, tune narrowly, document exceptions and test.

Every SOC analyst knows the feeling of opening the queue and seeing the same alert for the hundredth time. Tuning those rules was one of the most useful things I did as an analyst. It contributed to a 30% reduction in false positives across the clients we monitored. This is the approach I follow.

Why false positives are a security problem

Noise is not only annoying. Every alert an analyst has to close as benign takes time away from the ones that matter, and a queue full of repeats teaches people to close alerts quickly. That is exactly the habit an attacker benefits from. The goal of tuning is not fewer alerts. It is a queue where most alerts deserve attention.

1. Measure before you change anything

Start with data, not with the rules people complain about most. For a period of at least two to four weeks, count for each rule:

  • how many alerts it raised,
  • how many were closed as benign or false positive,
  • how many led to a real investigation or incident.

In most environments a small number of rules produce most of the noise. Those are where tuning pays off first.

2. Find out why each noisy rule fires

Read a sample of the benign alerts for each noisy rule and look for the pattern. The usual causes are:

  • Known, approved activity: vulnerability scanners, backup jobs, monitoring tools and administrators doing their jobs.
  • Thresholds that do not fit the environment: a login failure threshold that suits a small office but not a domain controller serving thousands of users.
  • Parsing problems: fields extracted wrongly, so the rule matches things it was never meant to match.
  • Rules that are too broad: written to catch a technique in general, without the context that makes it suspicious.

3. Tune narrowly, never by switching rules off

Disabling a noisy rule removes the noise and the detection together. Instead, make the smallest change that removes the benign pattern:

  • Exclude a specific host, account or process, not a whole subnet.
  • Adjust thresholds per group of assets, rather than one value for everything.
  • Add context, such as time of day or whether the source is internal, so the rule fires on the suspicious version of the behaviour.
  • Fix the parsing first if the fields are wrong. Tuning around a parsing bug only hides it.

Mapping each rule to the MITRE ATT&CK technique it is meant to detect helps here. It forces the question: after this change, would the rule still catch that technique?

4. Write every exception down

Exceptions are where attackers hide. An excluded server is a server whose activity nobody will see. For each exception, record what was excluded, why, who approved it and when it should be reviewed. Then review the list regularly. Assets change owners, scanners are retired and service accounts get reused.

5. Test against real attacks, not just real noise

Before and after a change, check that the rule still fires on the activity it exists for. Replay historical true positives if your SIEM allows it, or generate a safe test event in a lab. A rule that has gone quiet because it was tuned too far looks exactly like a rule with nothing to detect.

6. Measure again

Repeat the counts from step 1 after a few weeks. You want the benign rate of each tuned rule to fall while its true positives stay the same. If true positives also drop, the tuning went too far.

Summary

  • Measure alert volume and outcomes per rule before changing anything.
  • Understand why a rule is noisy, and fix parsing problems first.
  • Tune with narrow, documented exceptions. Do not disable rules.
  • Prove the rule still catches the technique it was written for.
  • Measure again, and review exceptions regularly.
