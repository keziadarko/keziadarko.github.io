When the SIEM disk fills up: a checklist for Graylog

A full disk on a SIEM server is not only a storage problem. It is a detection problem, because the rules keep running while the data they depend on stops arriving.

I recently investigated a disk usage issue on a Graylog server. This post is the checklist I would follow again: find what is using the space, check retention, check whether data is still being written, and only then free space.

Why a full disk is a detection problem

Graylog stores messages in an OpenSearch or Elasticsearch cluster. That cluster protects itself with disk watermarks. With the default settings, at 85% disk usage a node stops receiving new shards, at 90% the cluster tries to move shards away, and at 95% (the flood stage) indices are made read-only. Your values may differ if someone has changed them.

Once indices are read-only, Graylog cannot write new messages. It keeps them in its on-disk journal, which grows on the same server. If the journal fills, messages are lost. Meanwhile dashboards still load and alerts still run, just against data that stopped at some point. Nothing looks broken until someone notices the gap.

1. Find out what is using the space

Start on the server itself. Check which file system is full, then which directory is growing.

df -h
sudo du -xh --max-depth=1 /var/lib 2>/dev/null | sort -h | tail -n 10
sudo du -xh --max-depth=1 /var/log 2>/dev/null | sort -h | tail -n 10

On a package install, the usual suspects are:

WhatTypical location
Search indices/var/lib/opensearch or /var/lib/elasticsearch
Graylog message journal/var/lib/graylog-server/journal
MongoDB (configuration)/var/lib/mongodb
Application logs/var/log/graylog-server, /var/log/opensearch

Paths change with Docker or a custom install, so confirm them in the configuration: path.data in the OpenSearch configuration and message_journal_dir in Graylog's server.conf.

2. Check the indices and retention

If the index data is the largest directory, list the indices by size and check how full each node is. These commands assume a single node on localhost:9200 without authentication. Add credentials and HTTPS if your cluster uses them.

curl -s 'http://localhost:9200/_cat/allocation?v'
curl -s 'http://localhost:9200/_cat/indices?v&s=store.size:desc' | head -n 20

Then open System > Indices in Graylog and look at each index set. The questions I ask are:

  • Is a retention strategy actually set, or is it set to keep everything?
  • Does the maximum number of indices, multiplied by the size of each index, fit on the disk?
  • Has a new index set or stream been added recently without its own retention?
  • On newer Graylog versions that use data tiering, are the minimum and maximum days in storage realistic for the disk?

3. Check whether data is still being written

Next, find out whether the server is keeping up. Graylog's journal shows how many messages it has received but not yet written to the indices.

curl -s -u admin 'http://localhost:9000/api/system/journal'

If the number of uncommitted entries is high and rising, Graylog is receiving faster than it can write. A growing journal is a symptom, not the cause, so look at the output side: read-only indices or an unhealthy cluster.

To check for read-only indices:

curl -s 'http://localhost:9200/_all/_settings?filter_path=*.settings.index.blocks&pretty'

If you see read_only_allow_delete, the flood stage has been reached. Recent versions remove this block automatically once usage falls below the high watermark. On older versions you may have to clear it yourself after freeing space.

4. Look at what changed in ingest

Disk usage is roughly daily ingest multiplied by retention. If retention has not changed, ingest probably has. In Graylog, search the last 30 days and count messages by source to see which one grew. Common causes are a device switched to debug logging, a firewall that started logging all allowed traffic, or a new log source onboarded without a sizing check.

Reducing volume at the source is usually better than dropping messages in Graylog, but agree it with the team that owns the source. Some noisy logs still have detection value.

5. Free space safely

  • Do not delete files inside the index data directory by hand. Graylog and OpenSearch will no longer agree on what exists.
  • Delete the oldest indices from the index set in Graylog, or lower the maximum number of indices and let retention remove them.
  • Clean up old rotated application logs, and check that log rotation is configured.
  • Afterwards, confirm that the journal is draining and that new messages appear in searches.

Size it so it does not happen again

Work out the disk you need as daily ingest on disk, multiplied by the retention period in days, multiplied by one plus the number of replicas. Then make sure the result stays comfortably below the low watermark, not just below 100%.

Finally, monitor disk usage on the SIEM like any other critical system, and alert well before 85%. The point is to find out from an alert, not from a gap in the data.

Summary

  • A full SIEM disk silently stops detection, so treat it as a security issue.
  • Find the growing directory first, then check index retention, the journal and read-only blocks.
  • Find what changed in ingest before deleting anything.
  • Free space through Graylog, never by deleting index files.
  • Size storage against the watermarks and alert on disk usage early.

Commands and default values vary between Graylog, OpenSearch and Elasticsearch versions. Check them against the documentation for your version before running them in production.
